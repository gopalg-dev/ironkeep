# Offline data for an Expo gym logbook: storage, persistence, export/import, email, backups

Research date: 2026-10-21. Current versions seen on npm that day: `expo` 58.0.16 (SDK 58 stable; `sdk-54` tag = 54.0.37), `expo-sqlite` 58.0.13, `drizzle-orm` latest 0.45.4 (rc 1.0.0-rc.4), `@op-engineering/op-sqlite` 18.2.5, `react-native-mmkv` 4.3.2, SheetJS `xlsx` 0.20.3 (CDN only; npm registry stuck at 0.18.5).

## Recommendations (one line per decision)

1. **Database:** `expo-sqlite` + Drizzle ORM (`drizzle-orm/expo-sqlite`, `useLiveQuery`, `useMigrations` with bundled `drizzle/migrations.js`); a few thousand rows is far below where op-sqlite or WatermelonDB pay off, and expo-sqlite runs in Expo Go, dev builds and the New Architecture. Use MMKV/`expo-sqlite/kv-store` only for tiny UI prefs, never for records.
2. **Migrations:** `drizzle-kit generate` -> commit the `drizzle/` folder -> `useMigrations(db, migrations)` at startup (or in `SQLiteProvider onInit`), plus `PRAGMA journal_mode = WAL` once. Pin `drizzle-orm`/`drizzle-kit` to the stable 0.45.x line (the docs' `@rc` tags are 1.0 pre-releases).
3. **Persistence across updates:** app-private storage (`Paths.document`, the DB in `<filesDir>/SQLite/`) survives any in-place APK update; it is wiped only by uninstall or "Clear data". An update is accepted only if the package name matches, the signing certificate matches and `versionCode` is not lower. Publish the rule: one `applicationId`, one release keystore for the lifetime of the app, `versionCode` bumped every release.
4. **OSS signing rule:** do not ship releases signed with the template's `debug.keystore` (the Expo bare template signs `release` with `signingConfigs.debug` by default); keep one private `release.keystore` out of git (EAS remote credentials or `credentials.json`, git-ignored). Anyone building their own APK gets their own key and must uninstall yours first, so tell them to export before switching builds.
5. **OS backup:** leave `android.allowBackup` at its default `true` (Auto Backup already includes `getFilesDir()` and databases, 25 MB cap, needs a Google account + backup enabled) and let iOS back up `Documents/` to iCloud; treat both as a bonus, never as the app's backup story.
6. **File API:** use the SDK 54+ `expo-file-system` object API (`File`, `Directory`, `Paths`) for everything new; import `expo-file-system/legacy` only for `StorageAccessFramework` helpers if you need `createFileAsync`/`readDirectoryAsync` on a `content://` tree (the new `Directory.pickDirectoryAsync()` already takes a persistable permission).
7. **Export (primary):** write `plates-backup-YYYY-MM-DD.json` (and optionally `.csv`/`.xlsx`) into `Paths.cache`, then `Sharing.shareAsync(file.uri, { mimeType })`; the Android share sheet reaches Gmail, Drive, Files, Nearby Share, etc. Offer "Save to folder" (SAF) as the second option.
8. **Spreadsheet:** SheetJS 0.20.3 from `cdn.sheetjs.com` works in RN/Expo (write `type: 'base64'`, save with `File.write(b64, { encoding: 'base64' })`); CSV is cheaper and lossless for a logbook, so make `.xlsx` optional and keep `.json` the canonical format. Skip exceljs (Node `Buffer`/streams polyfills) and write-excel-file (no RN target).
9. **Import:** `File.pickFileAsync({ mimeTypes })` (SDK 56+ options form) or `expo-document-picker` with `copyToCacheDirectory: true`, then `file.text()` for JSON/CSV (UTF-8) or `file.base64()` + `XLSX.read(b64, { type: 'base64' })`; always go through the cache copy rather than the raw `content://` URI.
10. **Email:** primary path is the share sheet (user picks Gmail; attachments work because expo-sharing wraps the file in its own FileProvider). `expo-mail-composer` is a fine "Email it" button on Android when `isAvailableAsync()` is true (it also uses a FileProvider covering `files/` and `cache/`), but Android always reports "sent" and iOS needs the Apple Mail app set up; `mailto:` is the no-attachment fallback. No server-side mail.
11. **Automatic backups:** (a) write a JSON snapshot into `Paths.document/backups/` on app foreground when the last one is older than N days (zero permissions, survives updates, dies with uninstall) and (c) if the user picks a folder once via SAF, also write the snapshot there (survives uninstall, permission persists across restarts and updates). `expo-background-task` is unreliable for this (min 15 min, system-decided, vendor-killed); Google Drive sign-in is out.
12. **Data-safety patterns:** WAL + transactions for atomic writes; export via `VACUUM INTO` or a JSON dump built inside one read transaction (never raw-copy `app.db` without its `-wal`); every export carries `{ app, schemaVersion, exportedAt, appVersion }`; import is idempotent (stable UUIDs per row, upsert by id); first-launch screen offers "Restore from file"; a quiet "Last export: 12 days ago" line in Settings, no nags.
13. **Distribution:** GitHub Releases APK (+ Obtainium-friendly naming) with monotonically increasing `versionCode`; `expo-updates` is irrelevant for a no-server app, set `updates.enabled: false`. Watch Google's developer-verification rollout (store installs in 4 countries since 2026-09-30, global 2027).
14. **iOS later:** add `UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace` under `ios.infoPlist` so the Documents folder (and the backups subfolder) shows up in the Files app; `Documents/` is iCloud-backed up by default; share sheet and MailComposer work the same way.

### Drizzle + expo-sqlite: how migrations work

Official guides: https://orm.drizzle.team/docs/connect-expo-sqlite and https://orm.drizzle.team/docs/get-started/expo-new
1. `npx expo install expo-sqlite`; `npm i drizzle-orm`; `npm i -D drizzle-kit babel-plugin-inline-import`.
   The Drizzle docs currently show `drizzle-orm@rc` / `drizzle-kit@rc` (1.0.0-rc.4) and `expo-sqlite@next`; npm `latest` is 0.45.4 for drizzle-orm and 58.0.13 for expo-sqlite (the `next` tag points at the same 58.0.13). The expo driver has shipped since 0.30.x (op-sqlite driver + "fixed migration hook for Expo driver" in v0.30.1, 2024-03-08; `useLiveQuery` since v0.31.1, 2024-06-04: https://orm.drizzle.team/docs/latest-releases). Pin stable 0.45.x unless you want to track the 1.0 RC.
2. `babel.config.js`: `plugins: [['inline-import', { extensions: ['.sql'] }]]` so the generated `.sql` files are bundled as strings (Metro cannot read files at runtime).
3. `metro.config.js`: `config.resolver.sourceExts.push('sql')`.
4. `drizzle.config.ts`: `{ schema: './db/schema.ts', out: './drizzle', dialect: 'sqlite', driver: 'expo' }` — `driver: 'expo'` is what makes drizzle-kit emit `drizzle/migrations.js` (a JS module that imports every `.sql` via the inline-import plugin plus a `journal`) instead of expecting a filesystem at runtime.
5. `npx drizzle-kit generate` after every schema change; commit `drizzle/` (sql files + `meta/` journal + `migrations.js`).
6. Runtime: `const expo = openDatabaseSync('plates.db', { enableChangeListener: true }); const db = drizzle(expo, { schema }); const { success, error } = useMigrations(db, migrations)` from `drizzle-orm/expo-sqlite/migrator`. Drizzle records applied migrations in its own `__drizzle_migrations` table keyed by hash/created-at, so each bundled migration runs once per device, in order, inside the app at startup. Render a loading state until `success`.
7. Live data: `useLiveQuery(db.select().from(sets).where(...), [deps])` re-runs when the SQLite change listener fires. It needs `enableChangeListener: true` at open, otherwise nothing updates (the most common "not updating" report: https://github.com/drizzle-team/drizzle-orm/discussions/2447 and the v0.31.1 notes https://orm.drizzle.team/docs/latest-releases/drizzle-orm-v0311). Pass dynamic `where` values in the dependency array.

Gotchas:
- New Architecture: expo-sqlite and Drizzle are plain Expo Modules + JS; no known New-Arch-specific issue surfaced in the search (Ischys ships SDK 57 + New Architecture + expo-sqlite + Drizzle, see section 8).
- Expo Go: expo-sqlite works there (SQLCipher does not). Drizzle, migrations and `useLiveQuery` are pure JS, so the whole stack runs in Expo Go; a dev build is only needed once you add op-sqlite, MMKV, or any config-plugin-only feature (`useSQLCipher`, `withSQLiteVecExtension`).
- `openDatabaseSync` + `useMigrations` run on the JS thread at startup; expo-sqlite warns "heavy tasks can block the JavaScript thread" for the sync variants. Migrations for a few thousand rows are milliseconds.
- WAL is NOT the default; run `PRAGMA journal_mode = WAL` once (persistent). Also the `directory` option is unsupported on web only.
- DB path: Android `defaultDatabaseDirectory = context.filesDir.canonicalPath + "/SQLite"` (source: https://github.com/expo/expo/blob/main/packages/expo-sqlite/android/src/main/java/expo/modules/sqlite/SQLiteModule.kt); i.e. `<Paths.document>/SQLite/plates.db` plus `-wal`/`-shm` sidecars when WAL is on. Pass a custom `directory` only if you have a reason.
- `drizzle-studio-expo` dev-tools plugin lets you browse the on-device DB from the Expo CLI (Shift+M). The CLI also has a built-in "Open expo-sqlite" inspector.

## 2. Data persistence across app updates on Android

Facts, with sources:
- App-specific internal storage (`filesDir`, `databases`, `cacheDir`) is private to the app and "When the user uninstalls your app, the files saved in app-specific storage are removed." The cache dir may be purged by the system when storage is low. (https://developer.android.com/training/data-storage/app-specific) Nothing in that doc clears data on an update: an in-place update keeps the same UID and data directory, which is why Auto Backup documents restore only "when the app is installed", not updated. "Clear data"/"Clear storage" in system settings is the other wipe path.
- Update acceptance: "When the system is installing an update to an app, it compares the certificate(s) in the new version with those in the existing version. The system allows the update if the certificates match. If you sign the new version with a different certificate, you must assign a different package name to the app—in this case, the user installs the new version as a completely new app." (https://developer.android.com/studio/publish/app-signing). The failure you see is `INSTALL_FAILED_UPDATE_INCOMPATIBLE`; the only way forward is uninstall (which deletes the data) then install.
- Version codes: "users can't install an APK with a lower versionCode than the one already installed" (`INSTALL_FAILED_VERSION_DOWNGRADE`); increase `versionCode` monotonically each release; max 2100000000 (https://developer.android.com/studio/publish/versioning). Expo: `android.versionCode` in app config "must be incremented for each release" (https://docs.expo.dev/versions/latest/config/app/).
- Debug keystore: Android's debug cert is "insecure by design"; the Expo bare template ships `android/app/debug.keystore` (`storePassword 'android'`, `keyAlias 'androiddebugkey'`) and, crucially, the `release` build type uses `signingConfig signingConfigs.debug` with the comment "Caution! In production, you need to generate your own keystore file." (https://github.com/expo/expo/blob/main/templates/expo-template-bare-minimum/android/app/build.gradle). Expo's docs say debug keystores are the one kind you may commit, release keystores never (https://docs.expo.dev/app-signing/app-credentials/).
- EAS credentials: `eas build` signs with the keystore associated with the project on EAS; download/backup via `eas credentials -p android` -> credentials.json (https://docs.expo.dev/app-signing/app-credentials/). Local credentials: `credentials.json` with `android.keystore.{keystorePath,keystorePassword,keyAlias,keyPassword}`, `"credentialsSource": "local"` in eas.json, keystore in `android/keystores/`, both git-ignored; CI restores from base64 env vars (https://docs.expo.dev/app-signing/local-credentials/). Local release build: generate `my-upload-key.keystore` with keytool, put it in `android/app`, gradle.properties vars, `./gradlew app:assembleRelease`/`bundleRelease` (https://docs.expo.dev/guides/local-app-production/).

Rules to state in the README of an open-source project:
1. The official APK is always signed with the maintainer's private release key. Every release increments `versionCode`. Installing a newer official APK over an older one keeps all data.
2. If you build the APK yourself, Gradle signs it with your own (or the template debug) key. Android will refuse to install it over the official build (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) and vice versa; the only path is uninstall, which deletes the database. Export first (Settings > Export) and import after.
3. Never change `android.package` (applicationId) and never rotate the release keystore. Keep the keystore outside git (EAS remote credentials or a git-ignored `credentials.json`). Losing it means every existing user must uninstall to update.
4. `expo run:android` dev builds use `debug.keystore` and can be installed over each other across machines only if the same `debug.keystore` file is used (the template keeps it in the repo for exactly this reason).

## 3. Android Auto Backup and iOS iCloud backup

Android (https://developer.android.com/identity/data/autobackup, page updated 2026-02-26):
- Opt-in by default for `targetSdk >= 23`; `android:allowBackup` defaults to `true`. Backed up: shared prefs, `getFilesDir()`, `getDatabasePath()` databases, `getExternalFilesDir()`. Excluded: `getCacheDir()`, `getCodeCacheDir()`, `getNoBackupFilesDir()`. So the expo-sqlite file under `filesDir/SQLite/` and any JSON snapshot under `Paths.document` are included; anything in `Paths.cache` is not.
- 25 MB per app, only the latest backup kept, needs a Google account with device backup enabled, runs roughly every 24 h when idle on Wi-Fi; "During a backup the system shuts the app down so it isn't writing to the file system" (so the SQLite file is consistent, WAL sidecar included since it is also in filesDir). Restore happens on install from Play / device setup / `adb install`, before first launch.
- Android 12+: `android:dataExtractionRules` XML with separate `<cloud-backup>` and `<device-transfer>` sections; `allowBackup=false` may still allow device-to-device transfer on some OEMs.
- Expo exposure: `android.allowBackup` (boolean, default true: "Controls whether user app data is backed up to Google Drive") in app.json (https://docs.expo.dev/versions/latest/config/app/). There is no app.json key for `dataExtractionRules`; you would need a small config plugin if you wanted to exclude files.
- Verdict: keep it on (free, silent restore for Play/Google users), but an open-source APK user may have no Google backup, may be over 25 MB after years of logs, and restore only triggers on reinstall; so the app's own export is the real guarantee.

iOS (Apple File System Programming Guide, archive): https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html
- `Documents/` "backed up by iTunes and iCloud"; `Library/Application Support` backed up; `Library/Caches` and `tmp/` not backed up and may be purged. Expo's `Paths.document` maps to `Documents/`, `Paths.cache` to `Library/Caches`. expo-sqlite's iOS default directory is also under the document directory, so the DB rides along with iCloud backup unless you exclude it with `isExcludedFromBackup` (no Expo API; a config plugin or native code would be needed; not recommended here).

expo-file-system API (SDK 54+):
- SDK 54 (2025-09-16, https://expo.dev/blog/expo-file-system) made the object API the default import: `File`, `Directory`, `Paths` (`Paths.document`, `Paths.cache`, `Paths.appleSharedContainers`), `file.write(text | base64, { encoding })`, `file.text()`, `file.base64()`, `file.bytes()`, `file.copy/move`, `file.contentUri` (Android `content://` for other apps), `File.pickFileAsync(options)` (options form since 56.0.0, 2026-05-05; multi-file + MIME list), `Directory.pickDirectoryAsync()` (Android+iOS since 19.0.11, 2025-09-10). Changelog: https://github.com/expo/expo/blob/main/packages/expo-file-system/CHANGELOG.md ("19.0.0 (2025-08-13): Make the modern filesystem API the default, move previous one to `expo-file-system/legacy`"; "19.0.0: [next] Add full support for SAF Uris"; "56.0.0: [Android] Fix copy/move support for SAF and content provider URIs"; "58.0.0 (2026-09-10): Fixed FileHandle security-scoped access, and non-SAF content:// URI support"; "58.0.3 (2026-09-28): [Android] Check permissions for content:// URIs served by the app's own file providers").
- Legacy (`expo-file-system/legacy`, https://docs.expo.dev/versions/latest/sdk/filesystem-legacy/): `documentDirectory`, `cacheDirectory`, `readAsStringAsync`/`writeAsStringAsync` (`utf8` default or `base64`), `StorageAccessFramework.requestDirectoryPermissionsAsync` (Android 11+ per docs), `createFileAsync(parentUri, name, mime)`, `readDirectoryAsync`, `makeDirectoryAsync`, `getContentUriAsync`. `readAsStringAsync`/`writeAsStringAsync` reject plain `content://` but accept SAF URIs; `getInfoAsync`/`copyAsync` accept `content://`. Still shipped "for backward compatibility"; calling legacy names from the root import throws at runtime.

## 4. Export files and hand them to the share sheet / a user-picked location

Share sheet (`expo-sharing` 58, https://docs.expo.dev/versions/latest/sdk/sharing/; source https://github.com/expo/expo/blob/main/packages/expo-sharing/android/src/main/java/expo/modules/sharing/SharingModule.kt):
- `Sharing.shareAsync(fileUri, { mimeType, dialogTitle, UTI })`. Android: only `file://` URLs are accepted ("Only local file URLs are supported (expected scheme to be 'file'..."), the file must be inside a path the app may read, and it is wrapped with `FileProvider.getUriForFile(ctx, packageName + ".SharingFileProvider", file)`; provider paths cover `files-path`, `cache-path` and `external-path` root (`sharing_provider_paths.xml`), so anything under `Paths.cache` or `Paths.document` shares fine. It builds `ACTION_SEND` + `EXTRA_STREAM` + `FLAG_GRANT_READ_URI_PERMISSION` (and grants to every resolved activity), wrapped in `createChooser`. Works in Expo Go. On iOS the `mimeType`/`UTI` only influence the extension; name the file with the right extension yourself.
- Pattern: `const f = new File(Paths.cache, 'plates-backup-2026-10-21.json'); f.write(JSON.stringify(payload)); await Sharing.shareAsync(f.uri, { mimeType: 'application/json', dialogTitle: 'Export' })`. Clean old files in `Paths.cache/exports` on launch.

Save to a user-picked folder (SAF):
- New API: `const dir = await Directory.pickDirectoryAsync()` -> returns a `Directory` backed by a `content://` tree URI; `new File(dir, 'name.json').create(); .write(...)` (the 19.0.0 "full support for SAF Uris" entry). The Android `FilePickerContract` builds `ACTION_OPEN_DOCUMENT_TREE` and in `parseResult` calls `contentResolver.takePersistableUriPermission(uri, flags & (READ|WRITE))` (source: https://github.com/expo/expo/blob/main/packages/expo-file-system/android/src/main/java/expo/modules/filesystem/FilePickerContract.kt), so the grant is persisted. SAF `content://` files only support `ReadOnly`/`Append` modes in `FileHandle`, `seek()` has no effect (docs).
- Legacy API: `StorageAccessFramework.requestDirectoryPermissionsAsync()` also takes the persistable permission in `OnActivityResult` (source: https://github.com/expo/expo/blob/main/packages/expo-file-system/android/src/main/java/expo/modules/filesystem/legacy/FileSystemLegacyModule.kt), then `createFileAsync(directoryUri, 'plates-backup', 'application/json')` + `writeAsStringAsync(safUri, text)`.
- Android 11+ limits: the picker cannot grant the root of internal storage, the `Download` folder root, or `Android/data` / `Android/obb` (https://developer.android.com/training/data-storage/shared/documents-files). Persisted grants die if the folder is moved/deleted; the framework caps persisted grants at 128 per app (https://issuetracker.google.com/149315521).
- `expo-document-picker` picks files only; folders go through `Directory.pickDirectoryAsync`/SAF.

SheetJS in React Native (https://docs.sheetjs.com/docs/demos/mobile/reactnative/, page updated 2026-08-03; install note https://docs.sheetjs.com/docs/getting-started/installation/frameworks/):
- Install from the CDN tarball (`npm i --save https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`); the npm registry `xlsx` is frozen at 0.18.5 ("the registry is out of date").
- Expo demo: write `XLSX.write(wb, { type: 'base64', bookType: 'xlsx' })` then `writeAsStringAsync(path, b64, { encoding: 'base64' })` (new API: `file.write(b64, { encoding: 'base64' })`); for a user folder on Android it uses `StorageAccessFramework.requestDirectoryPermissionsAsync` + `createFileAsync` + base64 write. Read: `getDocumentAsync({ copyToCacheDirectory: true })` -> `readAsStringAsync(uri, { encoding: 'base64' })` -> `XLSX.read(b64, { type: 'base64' })`. `XLSX.readFile`/`writeFile` do NOT work in RN (no fs); tested on RN 0.76/0.79 (2025).
- Caveats: pure JS, runs on the JS thread; base64 round-trips inflate memory by about 4/3 and the whole workbook is in memory. For a logbook (thousands of sets, a few hundred KB) this is a non-issue; keep heavy exports off the UI thread with `InteractionManager`/a spinner. No public Hermes-specific perf issue surfaced in the search.
- Alternatives: `exceljs` is Node/browser-oriented (`writeBuffer` needs `Buffer` and stream polyfills in Expo: https://forums.expo.dev/t/how-to-move-from-nodejs-to-react-native-expo-buffer-crypto-bigint-etc/55278, tutorial https://betterprogramming.pub/generate-and-share-excel-styled-spreadsheets-using-react-native-e2034492c234) and only worth it for cell styling; `write-excel-file` documents browser/node/universal entry points only, no RN target (https://github.com/catamphetamine/write-excel-file). A hand-rolled CSV writer (quote fields, `\r\n`, UTF-8 with optional BOM for Excel) covers the "open in a spreadsheet" use case with zero dependencies.

## 5. Importing files

- Picking: `expo-document-picker` `getDocumentAsync({ type: ['application/json', 'text/csv', 'text/comma-separated-values', 'application/vnd.openxmlformats-officedocument.spreadsheetml.sheet', '*/*'], copyToCacheDirectory: true })` returns `{ canceled, assets: [{ uri, name, size, mimeType, lastModified }] }`; with `copyToCacheDirectory: true` (default) the file is copied into the app cache so every Expo API can read it (`file://`), at the cost of a copy for large files (https://docs.expo.dev/versions/latest/sdk/document-picker/). Or `File.pickFileAsync({ mimeTypes })` from the new file API (SDK 56+ signature), which hands back a SAF `content://`-backed `File` with a persisted read grant.
- Reading: `new File(uri).text()` for JSON/CSV (UTF-8 decode is done natively; the legacy `readAsStringAsync` default is also UTF-8); `.base64()` for `.xlsx` -> `XLSX.read(b64, { type: 'base64' })` -> `XLSX.utils.sheet_to_json(ws, { raw: true })`. Android MIME filters are unreliable for CSV (`text/csv`, `text/comma-separated-values`, `application/octet-stream` all show up); accept `*/*` and sniff by extension/content.
- Content URIs vs paths: Android pickers return `content://` URIs; `expo-document-picker`'s cache copy and `File.copy()` turn them into `file://` under your sandbox; legacy `readAsStringAsync` rejects non-SAF `content://`. Expo 58.0.3 added permission checks on `content://` URIs served by the app's own providers.
- Large files: a logbook export is small (tens of KB per year of training). If someone imports a multi-MB spreadsheet, parse on a `setTimeout`/after `InteractionManager.runAfterInteractions`, show progress, and insert in batches inside one transaction (`db.transaction` / `withTransactionAsync`), which is also what makes the import atomic.
- UTF-8/BOM: strip a leading `﻿` before `JSON.parse`/CSV parsing (Excel writes a BOM on "CSV UTF-8").

## 6. Emailing the export

`expo-mail-composer` (SDK 58, https://docs.expo.dev/versions/latest/sdk/mail-composer/):
- `composeAsync({ recipients, subject, body, isHtml, attachments: [fileUri] })`; `attachments` is "an array of the app's internal file URIs". Android source (https://github.com/expo/expo/blob/main/packages/expo-mail-composer/android/src/main/java/expo/modules/mailcomposer/MailIntentBuilder.kt and MailComposerModule.kt): with attachments it uses `ACTION_SEND_MULTIPLE`, converts each `file://` path with `FileProvider.getUriForFile(ctx, packageName + ".MailComposerFileProvider", file)` (falls back to `Uri.fromFile` if that throws), adds `FLAG_GRANT_READ_URI_PERMISSION` on the chooser, and offers every app that resolves `mailto:`. The provider paths are `files-path "."` and `cache-path "."` (`mail_composer_provider_paths.xml`), so put the attachment under `Paths.cache` or `Paths.document`, never external storage, and give it an extension (old forum reports of "no attachment"/`FileUriExposedException` came from files outside those roots or without an extension: https://forums.expo.dev/t/mailcomposer-attachments-not-working-android/7771 , https://forums.expo.dev/t/expo-mail-composer-sending-email-with-attachment-in-android-error/44245).
- `isAvailableAsync()`: Android = `packageManager.resolveActivity(ACTION_SENDTO mailto:) != null`, i.e. true only when some mail app is installed; iOS = `MFMailComposeViewController.canSendMail` (needs the Apple Mail app with an account; false under MDM; not on simulators). Result on Android is always `sent` ("Android does not provide this info"). `getClients()` lists installed mail clients. Works in Expo Go. `isHtml` "not working perfectly on Android".
- `expo-sharing`: the generic share sheet; the user picks Gmail/Outlook and the attachment arrives the same way (expo-sharing's own FileProvider). It is the more robust default because it also covers Drive, Files, Nearby Share, Telegram, etc. and never pretends to know the outcome.
- `Linking.openURL('mailto:?subject=...&body=...')`: no attachments, so only a fallback for a text note or a link.
- Recommendation: Settings > "Export" opens the share sheet (primary). "Email to myself" button: if `MailComposer.isAvailableAsync()` -> `composeAsync` with the user's saved address prefilled; else fall back to the share sheet; never a server.

## 7. Scheduled / automatic backups without a server

Options and their status:
- (a) In-app snapshot: on foreground (`AppState` 'active') or after a session is saved, if `lastSnapshotAt` is older than N days, write `Paths.document/backups/plates-YYYY-MM-DD.json` and prune to the last K. Needs no permission, no background execution, survives updates (and is included in Android Auto Backup / iCloud backup). It does not survive uninstall. Cost: a few ms. This is the baseline.
- (b) `expo-background-task` (SDK 53+, replaces `expo-background-fetch`, which is "deprecated ... not receiving patches and will be removed": https://docs.expo.dev/versions/latest/sdk/background-fetch/ ; https://expo.dev/blog/goodbye-background-fetch-hello-expo-background-task ; https://docs.expo.dev/versions/latest/sdk/background-task/): WorkManager on Android / BGTaskScheduler on iOS, `minimumInterval` in minutes (min 15, default 12 h), runs only with battery/network constraints, "may run later than expected, or not at all", vendor-specific killing (dontkillmyapp.com), tasks stop after a force-kill until the app is relaunched; needs `UIBackgroundModes: processing` on iOS; `triggerTaskWorkerForTestingAsync` only in dev builds. Fine as an opportunistic extra, not as the guarantee. Since (a) already runs whenever the user opens the app (which is when data changes), (b) adds little.
- (c) SAF folder: ask once ("Choose a backup folder" in Settings), `Directory.pickDirectoryAsync()`; Expo takes `takePersistableUriPermission` (section 4), and Android persists that grant "across device restarts" (https://developer.android.com/training/data-storage/shared/documents-files); it stays valid across app updates because the grant is tied to the package/UID, and is lost on uninstall (the GrapheneOS thread observes it is "cleared only by uninstall -> reinstall": https://discuss.grapheneos.org/d/31297) or when the folder is moved/deleted (then `pickDirectoryAsync` again). Store the tree URI in the DB/settings; on each in-app snapshot also `new File(dir, name).create()` + write; wrap in try/catch and surface "Backup folder unavailable" in Settings. Files in a user-visible folder (e.g. `Documents/Plates`) survive uninstall and show up in Drive/Files sync if the user syncs that folder. This is exactly what Flexify does (section 8).
- (d) Google Drive API with the user's account: needs OAuth sign-in and a Google Cloud project; out of scope for a no-account app. The user can get the same effect by picking a Drive-synced folder in (c) or sharing the export to Drive.
- Verdict: (a) always + (c) opt-in; skip (b) and (d).

## 8. Data-safety patterns and how OSS trackers do it

Patterns (with sources where they exist):
- Atomic writes: SQLite transactions are atomic; WAL gives atomic commit plus concurrent readers and is "significantly faster" (https://www.sqlite.org/wal.html). Wrap every multi-row write (finish session = N sets + bodyweight) in one `withTransactionAsync`/Drizzle `db.transaction`.
- Consistent DB copies: never copy `plates.db` alone while in WAL mode: "If a database file is separated from its WAL file, then transactions that were previously committed to the database might be lost" (wal.html). Use `VACUUM INTO 'file'` ("the generated output database is a consistent snapshot of the original database", output file must not exist or be empty: https://www.sqlite.org/lang_vacuum.html) via `db.execAsync`, or expo-sqlite's `serializeAsync()` (in-memory `Uint8Array` of the whole DB, fine at this size) / `backupDatabaseAsync`. Flexify instead runs `PRAGMA wal_checkpoint(FULL)` then copies the file. For a JSON export, read all tables inside one transaction so the snapshot is consistent.
- Atomic file writes: write to `name.tmp` then `tmp.move(final)` (new API `File.move`), so a crash never leaves a half-written backup; `VACUUM INTO` warns a power loss mid-command can leave a corrupt output file.
- Export envelope: `{ "app": "plates", "format": 1, "schemaVersion": <drizzle migration count or tag>, "appVersion": "1.4.0", "exportedAt": "2026-10-21T10:00:00Z", "data": { settings, plan, workouts, sets, bodyweight, measurements } }`. Import reads `format` and refuses newer-than-known versions with a clear message; older ones go through per-version upgraders (same shape as DB migrations, kept in `lib/export/upgrade.ts`).
- Idempotent import: give every row a stable UUID (`crypto.randomUUID()` from `expo-crypto`/Hermes) at creation; import = upsert by id (`INSERT ... ON CONFLICT(id) DO UPDATE`) inside one transaction; for rows without ids (CSV from other apps) dedupe on a natural key (exercise + date + set index). Offer "Merge" vs "Replace everything" and show a count preview before committing.
- Version-tagged migrations: Drizzle's journal already tags each migration with a timestamp/tag; also store `appVersion` in a `meta` table at each startup so a downgrade can be detected and refused (Android itself refuses lower `versionCode` installs, so this only matters for sideloaded dev builds).
- First launch: if the DB is empty, show a single "Start fresh / Restore from file" choice (and, on Android, if a SAF backup folder is remembered in Auto-Backup-restored settings, list the snapshots found there). This is informational, not a nag.
- Quiet reminder: Settings shows "Last export: 12 days ago" and "Backup folder: Documents/Plates (last backup yesterday)"; no banners, no modal prompts, per the app's no-pushing rule.
- Keep `Paths.cache` for transient export files only; everything you want kept lives in `Paths.document`.

Open-source trackers observed:
- **Flexify** (Flutter + Drift/SQLite, MIT; successor to the archived RN app Massive: https://github.com/brandonp2412/Massive "This app is now deprecated", GPL-3.0; https://github.com/brandonp2412/Flexify; F-Droid 2.2.34, 2026-10-15). Export page offers CSV (graphs, plans) and a full "backup" zip (database + images) saved via `FilePicker.saveFile`; import page restores from the zip; Settings has an "Automatic backups" switch: `MainActivity.kt` launches `ACTION_OPEN_DOCUMENT_TREE`, calls `contentResolver.takePersistableUriPermission(uri, takeFlags)`, stores `backup_path`, and `BackupReceiver.kt` writes the zip into the tree with `DocumentFile.fromTreeUri(...).createFile("application/zip", name)` after `PRAGMA wal_checkpoint(FULL)` + file copy (code read via the GitHub API on 2026-10-21). This is the closest reference implementation for pattern 7(c).
- **Ischys** (https://github.com/ischys-app/Ischys, MIT, Expo SDK 57 + New Architecture + expo-sqlite + Drizzle): "Nothing ever leaves the device"; export JSON or CSV any time, CSV import (Android), relies on OS device backup (iCloud / Google) otherwise. Android still in closed Play testing.
- **Skulpt** (https://github.com/skulptapp/skulpt, GPL-3.0, RN + Expo + SQLite + Drizzle, Expo Router): SQLite is the source of truth, writes complete locally first, a `sync_queue` table feeds an optional sync layer chosen at build time; Drizzle migrations generated with `bun run db:generate`, committed, and "applied at startup". No export/import documented in the README.
- **Liftosaur** (https://github.com/astashov/liftosaur, AGPL-3.0): Preact PWA wrapped as mobile apps; state persisted in IndexedDB (`keyval-store`/`keyval`, `src/utils/indexeddb.ts`); offline-first with optional cloud account; program sharing by link rather than file export.
- Other small Expo examples found: get-fitter (JSON backup export/import from the Profile tab), asfilion/workout-app (expo-file-system + expo-sharing CSV export): https://github.com/azizdahodwala/get-fitter , https://github.com/asfilion/workout-app.

## 9. Play-store-less Android distribution

- Updates keep data when (and only when): same `applicationId`, same signing certificate, `versionCode` strictly greater than installed (sections 2 and 9 sources: app-signing, versioning). Set `android.versionCode` in app.json or use EAS `autoIncrement`; name the asset `plates-v1.4.0.apk` and attach it to a GitHub Release tagged `v1.4.0`.
- Users install with "Install unknown apps" permission for their browser/Files app; Obtainium (GPL-3.0, https://github.com/ImranR98/Obtainium) can track a GitHub Releases page and install updates in place (same key => data kept).
- Google's developer-verification programme: enforcement started 2026-09-30 in Brazil, Indonesia, Singapore and Thailand for installs through participating stores; Google says direct downloads/other stores are not affected there until the global rollout planned for 2027, when an "advanced flow" (24 h lock, explicit opt-in) applies to unverified developers; `adb` installs stay possible (https://www.androidauthority.com/android-sideloading-changes-timeline-3679204/ , https://9to5google.com/2025/08/25/android-apps-developer-verification/ , https://foresightmobile.com/blog/android-developer-verification-2026). Plan to register as a verified developer (or publish on an alternative store) before 2027 if you want frictionless installs.
- `expo-updates` (https://docs.expo.dev/versions/latest/sdk/updates/): fetches JS bundles from a server implementing the Expo Updates protocol (EAS Update or self-hosted) over the network, keyed by `runtimeVersion`; it cannot change native code and does nothing to app data. For an app with no server and no network dependency it is pure dead weight and a privacy surface; set `"updates": { "enabled": false }` (then "the embedded update is loaded") and do not include the package. Releases are APKs with bumped `versionCode`. (op-sqlite also lists expo-updates as a conflicting package, another reason to leave it out if you ever switch drivers.)

## 10. iOS parity notes (for later)

- Files app visibility: set both `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` to true via `ios.infoPlist` in app.json; then the app's `Documents/` (so `Paths.document/backups/`) appears under Files > On My iPhone > Plates (iOS 11+). Community notes: the folder shows only once it contains at least one file; `LSSupportsOpeningDocumentsInPlace` means other apps open your documents in place, so keep the live SQLite file out of a user-editable tree, i.e. keep the DB in its default `SQLite/` subfolder and only expose JSON snapshots, or move the DB to `Library/Application Support` via `directory` if you want it fully hidden. (https://developer.apple.com/documentation/bundleresources/information-property-list/uifilesharingenabled , https://developer.apple.com/documentation/bundleresources/information-property-list/lssupportsopeningdocumentsinplace , https://developer.apple.com/forums/thread/765329 , https://developerinsider.co/how-to-access-document-directory-content-in-files-app)
- Backup: `Documents/` and `Library/Application Support` are in iCloud/Finder backups; `Caches` and `tmp` are not (section 3). Nothing to configure; app updates via TestFlight/App Store keep the sandbox.
- Export: `Sharing.shareAsync` presents `UIActivityViewController` (Save to Files, AirDrop, Mail, Drive). Give files the right extension; `UTI`/`mimeType` only append an extension if missing.
- Folder picking: `Directory.pickDirectoryAsync()` exists on iOS since expo-file-system 19.0.11 (2025-09-10); security-scoped access was fixed in 58.0.0. iCloud Drive via `expo-document-picker` needs `ios.usesIcloudStorage: true` (iCloud entitlement) for managed apps.
- Mail: `MailComposer.isAvailableAsync()` is false without the Apple Mail app configured or under MDM; fall back to the share sheet (Gmail/Outlook appear there).
- Background: `expo-background-task` needs `UIBackgroundModes: processing` (CNG adds it); still best-effort, so the same foreground-snapshot strategy applies.
- Signing/updates: App Store / TestFlight builds use Apple-managed signing; bundle identifier (`ios.bundleIdentifier`) plays the role of `applicationId` and must never change.
